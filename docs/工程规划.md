# Opencode Harmony 工程规划

> 一个运行在鸿蒙系统 / OpenHarmony 桌面（PC）上的 **Opencode Desktop** 桌面版。
> 本文档是工程级规划（brainstorm 产物），回答「做什么、怎么做、按什么顺序做、有哪些风险」。

---

## 1. 项目概述

**一句话定义**：将 [opencode](https://github.com/anomalyco/opencode) 的桌面形态移植到鸿蒙 PC 平台，复用 [harmonypc-electron](https://atomgit.com/jianguoxu/harmonypc-electron) 提供的「Electron on HarmonyOS」运行方案，工程组织方式参考 [deepseek-harness-desktop](https://github.com/fellow99/deepseek-harness-desktop)（同级目录 + 源码引用）。

| 维度 | 结论 |
|---|---|
| 目标形态 | 鸿蒙 PC 桌面应用（`deviceTypes: ["2in1"]`） |
| 功能对齐 | 与 Opencode Desktop 基本一致（AI 编码代理的桌面 GUI） |
| 技术底座 | harmonypc-electron（Electron 37 移植到 HarmonyOS） |
| 工程组织 | 同级目录 + 源码引用（**非 submodule**） |
| v1 目标 | **MVP 先行**（跑通核心链路，原生重依赖降级/桩） |
| 本工程 | `opencode-harmony`（当前已是 DevEco Studio 鸿蒙工程骨架） |

**非官方声明**：本工程名含 `opencode`，按 opencode 官方要求，README 需注明「本工程非 opencode 团队构建、与其无关」。实施时补上。

## 2. 参考工程调研结论

### 2.1 opencode —— 桌面端实现（`packages/desktop/`）

**技术栈**：Electron **42.3.3** + `electron-vite` + `electron-builder`；渲染层是 **SolidJS**（workspace 包 `@opencode-ai/app` + `@opencode-ai/ui`），不是 `packages/web`（那是 Astro/Starlight 文档站）。

**运行时架构 —— Sidecar 模式**（关键）：

```
Electron 主进程 (main/index.ts)
  └─ utilityProcess.fork(sidecar.js)          ← 独立 utility 进程
       └─ import "virtual:opencode-server"
            └─ Server.listen({ port, hostname: "127.0.0.1",
                               username: "opencode", password: <随机>,
                               cors: ["oc://renderer"] })
  渲染进程（SolidJS app）
    └─ 通过 sdk/client 连接 http://127.0.0.1:<port>（Basic 鉴权）
```

- 服务端由 `@opencode-ai/server` + `@opencode-ai/core` 构成，被 electron-vite 以虚拟模块 `virtual:opencode-server` 打包进 sidecar。
- 主进程还负责：单实例锁、托盘、菜单、自动更新（`electron-updater`）、上下文菜单、WSL 集成、崩溃上报（Sentry）等。

**重原生依赖**（鸿蒙移植的主要障碍）：

| 依赖 | 用途 | 鸿蒙风险 |
|---|---|---|
| `@lydell/node-pty` | 终端 PTY | 高（依赖 libuv+pty，需鸿蒙重编译） |
| `@parcel/watcher` | 文件监视（Rust napi） | 高（需鸿蒙重编译；opencode 另有 `chokidar` 纯 JS 兜底） |
| SQLite（drizzle-orm） | 存储 | 低（有内置 `node:sqlite` 可迁移；core `#sqlite` node 条件现指向 `better-sqlite3`，需小 patch 切换或编译，见 §8 O2） |
| ripgrep | 代码搜索 | 中（需鸿蒙版 rg 二进制或 JS 兜底） |
| `@silvia-odwyer/photon-node` | 图像处理 | 中（native 模块） |

**运行时关键事实**：`opencode` CLI 包是 **Bun 优先**（`bun.lock`、`@tsconfig/bun`、`#db` 的 `bun`/`node` 双条件、`@ff-labs/fff-bun`），但 **desktop 的 sidecar 已在 Electron 内嵌 Node 下跑通**，说明 `server` + `core` 的 Node 路径是通的（`#db` 走 `node` 条件）。

### 2.2 harmonypc-electron —— Electron 在鸿蒙的运行方案

- 将 **Electron** 移植到 HarmonyOS PC，仓库内提供多版本产物：**v34**（Node 20）、**v37.2.3**（Chromium 138 / Node 22.16）、**electron40 v40.0.0**（Chromium 144 / Node 24.11.1，含完整 `ohos_hap`）。原生库：`libelectron.so`（Electron 核心 + Node）、`libadapter.so`（鸿蒙适配层）、`libffmpeg.so`、`libc++_shared.so`（`arm64-v8a`）；40 额外带 `libvk_swiftshader.so`（软件渲染）与 `vscode-sqlite3.node`（预编译 SQLite addon）。
- **HAP 结构**（`ohos_hap/`）：
  - `electron/` 模块：原生 `.so` + C++ 源码 + ArkTS 绑定。
  - `web_engine/` 模块：ArkTS 适配层（`Index.ets`、`childProcess.ets`、`src/main/cpp`）。
  - **应用代码放置点**：`web_engine/src/main/resources/resfile/resources/app/`（把 Electron 应用（main.js + 资源）放这里）。
- **已支持 Electron 模块**：`app`、`BrowserWindow`、`ipcMain/ipcRenderer`、`Menu`、`Tray`、`Notification`、`dialog`、`shell`、`fs`、`path`。
- 提供 native 模块编译指引（如 better-sqlite3、node-sqlite3 的 node 头文件/编译文档），以及 `demos/system-info` 等示例。

**关键约束**：选定 **Electron 37**（Chromium 138 / Node 22.17.0，已被 deepseek-harmony 真机验证）。与 opencode desktop 的 Electron 42（Node 24.x）存在 Node 22→24 的差距，需 Phase 0 验证 opencode 服务端在 Node 22 下可跑（见 §8 R2）。

### 2.3 deepseek-harness-desktop —— 关联工程组织方式

- **同级目录 + 源码引用（非 submodule）**：`deepseek-harness-desktop/`、`deepseek-harness/`、`dsh-market/` 并行存放于同一父目录，桌面壳通过 `../deepseek-harness`、`../dsh-market` 相对路径引用源码。
- **对上游打补丁**：`patches/*.patch` 经 `git apply`（`--reverse --check` 幂等），构建脚本自动应用。
- **构建脚本编排**：`build-dsh.mjs`（apply patches → install → build lib/web → build market）、`collect-dsh.mjs`（pnpm deploy 物化产物到 `dsh-dist/`，`extraResource` 打进 Electron resources）。
- **桌面壳形态**：主进程内挂起 dsh Host + webserver，渲染进程同源 `loadURL(localhost)`，复用 `WebApiClient`，零 CORS/零鉴权/零自定义协议。
- **CI 说明**：GitHub Actions 需单独 clone 同级仓库（`actions/checkout` 无法把第二个仓库放进 `$GITHUB_WORKSPACE`）。

### 2.4 结论对照表

| 关注点 | opencode desktop | harmonypc-electron | deepseek-harness-desktop | **Opencode Harmony 取法** |
|---|---|---|---|---|
| 运行时架构 | Sidecar（服务端独立进程 + SolidJS 渲染层） | 提供 Electron 运行底座 | 进程内 Host + localhost 同源 | **utilityProcess.fork sidecar**（服务端跑 utility 进程，child_process 在其中可用，同 opencode desktop） |
| 前端表面 | SolidJS `@opencode-ai/app`+`ui` | 任意 Electron 应用 | 复用 dsh Web UI | 复用 opencode SolidJS 桌面 UI |
| 工程组织 | 自身 monorepo | 自身仓库 | 同级目录 + 源码引用 + 补丁 | **同级目录 + 源码引用 + 补丁** |
| 构建编排 | bun + electron-vite + electron-builder | DevEco/hvigor | host 侧脚本 build/collect | host 侧脚本 build/collect + hvigor 打包 |
| Electron 版本 | 42 | 34 / 37 / 40 | 最新稳定 | **37**（Chromium 138 / Node 22.17，已验证） |

### 2.5 deepseek-harness-harmony（同型已完成工程，最强参考）

**`../deepseek-harness-harmony` 是本工程的同型已完成工程**——用「Electron-on-HarmonyOS」封装 deepseek-harness（同为 agent harness），已在 **HAD-W24 / HarmonyOS 6.1.0.135（API 24）真机验证**（Electron 37 / Node 22.17.0，dsh Web UI 正常运行）。其 `docs/工程规划.md` 是「规划 + 最终实现记录」的完整范本，直接复用价值最高：

- **运行时选型**：从 ohos_electron_hap（Electron 34 / Node 20.18）切到 harmonypc-electron（Electron 37 / Node 22.17），因 Node 22 才有 `node:zlib.createZstdDecompress` + `node:sqlite`（Node 20 缺）。
- **三大鸿蒙适配**：① loopback 网络隔离 → webserver 绑 `0.0.0.0` + `loadURL(局域网 IP)`；② symlink 被禁（EACCES）→ 回退 `cpSync` 拷贝；③ 5 万+ 小文件打包超限 → tar.gz 压缩 + 运行时流式解压。
- **MVP 取舍**：node-pty/sharp/koffi 原生模块禁用/桩化（win32-x64 二进制无法在 aarch64 加载），node:sqlite 正常。
- **工程结构**：AppScope + electron(entry) + web_engine(HAR) + src-main + scripts（三阶段 collect-runtime → build-dsh → collect-dsh）+ patches + profiles，与本工程规划同构。

## 3. 核心决策

### 3.1 目录组织：同级目录 + 源码引用（非 submodule）✅ 已确认

- `opencode-harmony` 与 `opencode`、`harmonypc-electron` **并行存放**于同一父目录（当前磁盘布局已如此：`D:\oh-workspace\DevEcoStudioProjects\`）。
- 通过相对路径 `../opencode` 引用源码，对上游打补丁（`git apply`）+ 构建脚本编排，与 deepseek-harness-desktop 完全一致。
- **理由**：
  - 已被 dsh 参考工程验证可行，且当前磁盘已并行存放，零迁移成本。
  - submodule 会引入版本锁定/更新/克隆摩擦；vendor 化易漂移、同步成本高。
  - CI 需单独 clone 同级仓库（见 5.1）。

### 3.2 运行时架构：Sidecar（服务端）+ SolidJS 渲染层

镜像 opencode desktop 的 Sidecar 模式，但针对鸿蒙做适配：

```
鸿蒙 HAP（opencode-harmony）
├─ ArkTS 入口（EntryAbility / web_engine）→ 启动 Electron（libelectron.so）
└─ Electron 应用（打包进 web_engine/.../app/）
    ├─ 主进程
    │   ├─ fork 服务端（Node bundle）→ Server.listen(127.0.0.1:<port>)
    │   ├─ 窗口管理（BrowserWindow，无边框/自绘标题栏）
    │   └─ 托盘/通知/生命周期（MVP 阶段逐步补齐）
    └─ 渲染进程（SolidJS @opencode-ai/app+ui，静态 dist）
        └─ sdk/client → http://127.0.0.1:<port>（Basic 鉴权）
```

- 服务端 = `@opencode-ai/server` + `@opencode-ai/core` 的 **Node 兼容 bundle**（host 侧打包）。
- 渲染层 = `@opencode-ai/app` + `@opencode-ai/ui` 的 **静态 dist**（host 侧 vite build）。
- 与 dsh-desktop 的差异：dsh 原生入口是浏览器 Web UI（`dsh web`），桌面壳只是包一层；而 opencode 的桌面 GUI 本身就是 SolidJS 桌面 UI（`@opencode-ai/app` + `ui`），`packages/web` 是独立的 Astro 文档站、非应用界面。因此渲染层直接复用该 SolidJS 桌面应用，而非包一层第三方 Web UI。（注：opencode 服务端存在 `OPENCODE_DISABLE_EMBEDDED_WEB_UI` 开关，暗示其可能内嵌浏览器 UI；是否可作 `serve`+浏览器兜底，列入开放问题 O4 待验证，不影响 MVP 主方案。）

### 3.3 技术栈与版本约束

| 层 | 技术 | 版本/说明 |
|---|---|---|
| 运行时底座 | harmonypc-electron | Electron **37**（Chromium 138 / Node 22.17.0，已验证） |
| 服务端 | `@opencode-ai/server` + `core`（TS） | host 侧 bun/esbuild 打包为 Node bundle |
| 渲染层 | SolidJS `@opencode-ai/app` + `ui` | host 侧 vite 打包为静态 dist |
| 宿主工具链 | bun + node + electron-vite | 仅 host 侧，不进鸿蒙运行时 |
| 鸿蒙工程 | DevEco Studio 6.x + hvigor | SDK `6.1.1(24)`，`runtimeOS: HarmonyOS` |

#### Electron 版本选型（34 / 37 / 40 → 选定 37）

| 维度 | Electron 37 | Electron 40 | opencode desktop（参照） |
|---|---|---|---|
| Chromium | 138 | 144 | ~148 |
| Node | 22.17.0 | 24.11.1 | 24.x |
| V8 | 13.8 | 14.4 | ~14.x |
| 产物形态 | `v37.2.3-release.zip` | `electron40_...tar.gz`（完整 ohos_hap） | — |
| 构建日期 | 2026-08-25（更新） | 2026-06-29 | — |
| **真机验证** | ✅ **已验证**（deepseek-harness-harmony 在同型号设备 HAD-W24 跑通） | ❌ 无真机记录 | — |

**结论：选 Electron 37（Node 22.17.0），40 作为备选。** 理由：

1. **37 已被同类工程真机验证**：`deepseek-harness-harmony`（本工程同型参考，Electron-on-HarmonyOS 封装 agent harness）已在 **HAD-W24 / HarmonyOS 6.1.0.135**（本机同型号设备）用 Electron 37 / Node 22.17.0 跑通 Web UI。这是硬证据；40 尚无任何真机运行记录。
2. **Node 22.17 已含 opencode 所需内建能力**：`node:sqlite`（Node 22.5+）、`node:zlib.createZstdDecompress`（Node 22.15+）均内置。deepseek 从 Electron 34（Node 20）升到 37（Node 22）正因 Node 20 缺这两者。opencode 未发现 Node 24 独有硬依赖（待 Phase 0 确认）。
3. **Node 24.11（40）虽更接近 opencode 的 Electron 42（Node 24），但属「未验证的理论更优」**——若 Phase 0 发现 opencode 需 Node 24 独有 API，再切 40（产物已就绪，切换成本低）。

> 修正说明：早期评估曾倾向 Electron 40（Node 24 更接近上游 42），后发现 deepseek-harness-harmony 已在真机用 37 跑通，遂改为「**37 已验证优先**，40 备选」。

**版本差距**：opencode desktop 用 Electron 42（Node 24.x），选定 Electron 37（Node 22.17.0）。Node 22 vs 24 的差距需 Phase 0 验证 opencode 服务端在 Node 22 下能否启动（见 §8 R2）。

### 3.4 MVP 原生依赖降级策略

| 依赖 | MVP 策略 | 后续（Phase 2） |
|---|---|---|
| `@lydell/node-pty` | **禁用 PTY 终端**，降级为纯文本输入输出（或隐藏终端面板） | 鸿蒙 native 重编译 PTY |
| `@parcel/watcher` | 用 `chokidar`（纯 JS，opencode 已依赖）轮询兜底 | 编译 @parcel/watcher 的鸿蒙 native |
| SQLite | 优先迁移到 Node 内置 `node:sqlite`（`effect-sqlite-node` 已具备，需小 patch 绕开 core `#sqlite`→`better-sqlite3` 的 node 条件）；备选编译 better-sqlite3 | 走 `node:sqlite`，无需编译 |
| ripgrep | JS 搜索兜底 / 暂缺省 | 鸿蒙版 rg 二进制 |
| `photon-node`（图像） | 桩/禁用图像处理 | 鸿蒙 native 或纯 JS 替代 |

> 原则：**核心「会话 + 消息流 + 文件读写 + 工具调用」链路先跑通**，视觉/终端/搜索等增强能力后补。

> **已核实的 node 路径画像**（`core/package.json` 的 `imports` 有三处 bun/node 条件拆分 `#sqlite`/`#pty`/`#fff`）：node 分支均已存在——`#sqlite`→`better-sqlite3`（原生，未声明依赖，疑遗留，可迁移 `node:sqlite`）；`#pty`→`@lydell/node-pty`（原生）；`#fff`→**`available()=false` 优雅降级为 JS 搜索，无需原生编译**。文件查找/搜索因此不构成原生障碍。

### 3.5 MVP 落地关键决策（D1–D4）

| 决策点 | 决定 | 说明 |
|---|---|---|
| **D1 服务端打包** | **B：自建 esbuild/rollup 打包 `@opencode-ai/server`+`core` 为单文件 Node bundle** | 绕开 electron-vite 与 Electron 42 的耦合；产物为纯 Node 可执行 JS，需自行处理 `#sqlite`/`#pty`/`#fff` import 条件与 workspace 解析 |
| **D2 渲染层加载** | **`loadURL(局域网 IP)` + webserver 绑 `0.0.0.0`**（非 localhost） | 鸿蒙 NEXT 渲染进程访问 127.0.0.1 存在 **loopback 网络隔离**，必须绑全网卡 + 走局域网 IP（deepseek-harmony 已验证） |
| **D3 后端进程** | **utilityProcess.fork sidecar**（服务端跑 utility 进程，`child_process` 在其中可用；主进程 child_process 挂起） | 实测：utility 进程里 child_process 正常；同 opencode desktop 架构 |
| **D4 沙箱边界** | **已基本查清**（见下方结论）；唯一未决点是 `child_process.spawn` 命令执行 | Phase 0 第一优先实测 child_process |

**D4 验证结论**（基于 `deepseek-harness-harmony` 真机验证 + `harmonypc-electron` 源码）：

| 项 | 结论 |
|---|---|
| Node `fs` 读写 | ✅ 可用（应用沙箱/userData 内；deepseek 解压 555MB tar.gz 到 userData） |
| symlink | ❌ 被禁止（`EACCES`，需回退 `cpSync` 拷贝） |
| 网络 | ✅ 可用（`INTERNET` 权限），但 **loopback 被隔离**（渲染进程访问 127.0.0.1 失败，须绑 `0.0.0.0` + 局域网 IP） |
| `node:sqlite` | ✅ 可用（Node 22 内建） |
| 原生模块（node-pty/sharp/koffi） | ❌ 不可加载（win32-x64 二进制 vs aarch64），MVP 禁用/桩化 |
| `child_process.spawn`（命令执行） | ⚠️ **未验证**：鸿蒙 Electron 子进程走 `@ohos.app.ability.childProcessManager`（OS 级 ChildProcess ability，非 Linux fork/exec）；deepseek-harmony 禁用了 bash/shell 工具。**opencode 的 bash 工具依赖 `child_process.spawn`，是致命未决点，必须 Phase 0 实测** |

### 3.6 落地决策点（DP-1~7）与拍板

| # | 决策点 | 决定/建议 |
|---|---|---|
| DP-1 | opencode 渲染层（SolidJS UI）来源 | **✅ A：复用 SolidJS UI + web shim**。已 grep 验证 `@opencode-ai/app`/`ui` **无 electron 依赖**；electron 耦合全收敛在 desktop `renderer/index.tsx` 的 `createPlatform()`（把 `Platform` 接口接 `window.api`）。写一个 web `Platform`/`window.api` shim（`storage`→localStorage、`pickers`→`<input type=file>`、`notify`→Notification API、`awaitInitialization`→同源 URL）即可复用整个 UI。`ServerConnection` 已走 http（非 `oc://`），`oc://` 仅用于窗口加载 HTML |
| DP-2 | 渲染层→服务端鉴权/CORS | 同源 http 加载（服务端服务 API + 静态 dist），沿用 Basic auth，CORS 改同源（无 CORS）；需确认 SDK 支持自定义 auth header |
| DP-3 | 服务端打包成 Node bundle | **✅ bun + esbuild 打包**（opencode 本就是 bun 项目），`--conditions=node` 解析 `#sqlite`/`#pty`/`#fff`；AI provider **按需裁剪**（external 掉未用 provider，减小体积，连带缓解 R-A） |
| DP-4 | 外部二进制（git/sh/rg） | Phase 0 实测 `which sh git rg`；缺则打包静态 musl 二进制进 resfile，或用 JS 实现替代（搜索已有 fff 降级） |
| DP-5 | 数据目录 + 项目目录映射 | 数据目录 → `app.getPath('userData')`；项目目录 MVP 限定 Documents/Desktop（受 `READ_WRITE_*_DIRECTORY` 权限覆盖） |
| DP-6 | 签名配置 | **✅ 复用 deepseek-harmony 的签名**（已有 `electron-default-signed.hap`，本机签名可用），或 DevEco 自动签名 |
| DP-7 | 模块结构改造 | 移除 `entry` 占位模块，改为 `electron`(entry) + `web_engine`(HAR) + `src-main` + `scripts` + `patches` + `profiles`，照搬 deepseek-harmony 结构 |

## 4. 工程结构规划

### 4.1 目标目录结构（opencode-harmony 内部）

```
opencode-harmony/                       # 本工程（DevEco Studio 打开此根目录）
├── AppScope/                           # 鸿蒙应用全局配置（已存在）
```

## 5. 构建与打包流程

### 5.1 构建流水线（host 侧，Windows）

```
[前置] 同级源码就位（已存在）：
   ../opencode           （host 装 bun + node）
   ../harmonypc-electron （取 electron/web_engine 模块 + libs）

① patch-opencode.mjs     对 ../opencode 幂等应用 patches/（git apply --reverse --check）
② build-opencode.mjs     bun install → 打包 server+core 为 Node bundle
                          → vite build @opencode-ai/app+ui 为静态 dist
③ collect-app.mjs        物化产物（node bundle + dist + 必要 node_modules）
                          → web_engine/src/main/resources/resfile/resources/app/
④ DevEco/hvigor 构建     签名 + 打 HAP
⑤ 部署到鸿蒙设备/模拟器   运行验证
```

**CI 要点**（参考 dsh）：GitHub Actions 需在工作流里单独 clone `../opencode`（`actions/checkout` 无法把第二个仓库放进 `$GITHUB_WORKSPACE`）。

### 5.2 开发/调试循环

- **host 侧**：opencode 服务端/渲染层改动 → 重跑 ②③ → 重新打包 HAP。
- **鸿蒙侧**：ArkTS/窗口改动 → DevEco 增量编译 → 部署。
- 建议 Phase 0 阶段先在 host 用普通 Electron 验证「服务端 bundle + 渲染层 dist + 自定义主进程」的链路，再迁移到鸿蒙 Electron，缩小问题域。

## 6. MVP 范围定义

### 6.1 In scope（v1 必须达成）

- [ ] opencode 服务端（Node bundle）在鸿蒙 Electron 内启动，健康检查通过（`/api/health`）。

- [ ] 应用退出时正确停止服务端（Sidecar 生命周期）。

- ❌ 应用签名、商店分发、代码签名

## 7. 分阶段实施计划

### Phase 0 —— 可行性验证（✅ 已完成，2026-08-31 真机实测）

目标：**证明「opencode 服务端 + SolidJS 渲染层」能在鸿蒙 Electron 上运行**。

**实测结论**（真机 HAD-W24 / HarmonyOS 6.1.0.135，Electron 37 / Node 22.17.0）：

| 能力 | 结论 |
|---|---|
| `utilityProcess.fork` | ✅ 可用（spawn Node worker 成功回消息） |
| `child_process.spawn` | ⚠️ **主进程挂起，utility 进程正常** → 服务端跑 utility 进程 sidecar |
| `node:sqlite` | ❌ 不可用（"No such binding: sqlite"）→ 编译 better-sqlite3 或 WASM sqlite |
| `node:zlib.createZstdDecompress` | ✅ 可用 |
| `node:tls.setDefaultCACertificates` | ❌ undefined → 需替代方案加载系统 CA |
| 文件访问 | userData 沙箱 ✅；用户目录（Documents/Desktop/Downloads）经 `requestDirectoryPermission(路径)` 授权后 ✅ |
| symlink | ❌ EACCES → cp 递归拷贝替代 |
| 二进制 | 有 node/npm/python3/ls/grep/sed/awk/find 等；**无 git/rg/bash** |
| 网络 | ✅（INTERNET 权限） |

**结论：opencode 可行性基本成立。** 命令执行（utility 进程 sidecar）、文件读写（沙箱 + 授权目录）、LLM（网络）四大核心能力均有可行路径；git/rg/sqlite 需替代方案（打包静态二进制 / JS fallback / better-sqlite3 编译）。

> 完整实测记录 + 测试代码片段见 `D:\knowledge-base\鸿蒙\harmonypc-electron能力验证.md`。

### Phase 1 —— MVP（跑通核心链路）

在 Phase 0 基础上补齐：单窗口 + 标题栏、Sidecar 生命周期、核心工具调用、基础存储、README 非官方声明。

### Phase 2 —— 原生能力补齐

PTY 终端、@parcel/watcher、ripgrep 的鸿蒙 native 编译；托盘/通知/菜单。（SQLite 迁移到 `node:sqlite` 后无需编译）

### Phase 3 —— 分发与打磨

自动更新、签名、商店分发、性能/内存优化、多窗口。

## 8. 风险与开放问题

| # | 风险/问题 | 影响 | 缓解/验证方式 |
|---|---|---|---|
| R1 | Electron 42 → 37 API 差异（`setDefaultCACertificates`、Node 22 API 等） | 主进程需改写 | Phase 0 逐项验证，必要时降级实现 |
| R2 | ~~Node 版本差 / node:sqlite 不可用~~ **已解决**：better-sqlite3 预编译成品（12.4.5）真机加载成功（主+utility 进程，内存+文件库 CRUD 均 OK），仅需补 `libc++_shared.so`（.node 动态依赖）。`tls.setDefaultCACertificates` 仍 undefined，需替代 CA 方案 |
| R3 | opencode 核心 Bun 特化点 | 服务端跑不起来 | **已评估，面很小**：`server/src` 0 个 Bun API（纯 Node）；`core/src` 仅 1 个 `Bun.hash` + `#sqlite`/`#pty`/`#fff` 三处条件拆分的 bun 分支（node 分支已存在不生效） |
| R4 | node-pty / @parcel/watcher 等 native 模块鸿蒙编译难度高 | 终端/监视不可用 | MVP 降级（chokidar / 纯文本终端），Phase 2 编译 |
| R5 | ~~后端进程形态~~ **已定：utilityProcess.fork sidecar**（实测 utility 进程里 child_process 可用，见 R-B；主进程 child_process 挂起） | 已消除 | — |
| R6 | ripgrep / 图像处理等增强能力缺失 | 功能不完整 | 明确降级 + JS 兜底 |
| R7 | opencode 版本漂移（上游 dev 分支迭代快） | 补丁失效 | 锁定上游 commit/版本；patch 幂等化；README 记录 pinned 版本 |
| R8 | HAP 体积（Electron so + 服务端 bundle + 渲染层） | 安装包大 | tree-shaking、按需引入 provider、延迟加载 |
| R-A | **HAP 体积/打包超限**：opencode 服务端 node_modules（30+ provider + effect + drizzle + aws-sdk）可能远超 dsh 的 555MB | 打包失败/装不上 | 估产物体积；tar.gz 压缩 + 流式解压（同 dsh）+ provider 按需裁剪（DP-3） |
| R-B | ~~`child_process.spawn` 不可用~~ **已解决**：主进程挂起，但 **utility 进程（utilityProcess.fork）里正常**（status=0 返回输出）；服务端跑 utility 进程 sidecar 即可执行命令 | 已消除 | 服务端跑 utility 进程 |
| R-C | **opencode 服务端在 Node 22 下能否跑**（Node 24 独有 API？） | 服务端起不来 | 打包后 Node 22 下启动测健康检查（R2） |
| R-D | **渲染层剥离纯 web 构建难度**（`oc://`、`window.api` shim） | UI 出不来 | DP-1 已探明面很小（仅 `createPlatform` 接 `window.api`）；写 web shim |
| R-E | **Node bundle 打包 import 条件/原生模块解析**（`#sqlite`→better-sqlite3、`@ff-labs/fff-bun`） | 产物崩溃 | esbuild `--conditions=node` + 显式 external |
| R-F | **file watcher（chokidar）在沙箱下可用性**（symlink 禁止可能影响 fs.watch） | 文件监视失效 | 实测 chokidar，或禁用（轮询兜底） |
| R-G | **系统 CA + 代理**（LLM API 网络访问） | 调模型失败 | 复用 desktop `setDefaultCACertificates` + `NO_PROXY` |

**关键开放问题**（Phase 0 优先澄清）：
- O1：~~后端进程形态~~ **已定：utilityProcess.fork sidecar**（实测：utility 进程里 `child_process` 正常、主进程挂起；opencode desktop 的 sidecar 本就用 `utilityProcess.fork`，直接复用上游架构）。
- O2：~~opencode SQLite 实现~~ **已实测修正**：`node:sqlite` 在 Electron 37 上**不可用**（"No such binding: sqlite"）。core 的 `#sqlite` node 条件指向 `better-sqlite3`（原生，需编译）。方案：**编译 better-sqlite3**（37 有 node 头文件 + libshim.a 指南），或用 WASM sqlite。
- O3：~~Bun 特化点规模~~ **已量化**：`server/src` 0 个 Bun API；`core/src` 仅 1 个运行时 `Bun.hash`（`skill/discovery.ts`，可换 `node:crypto`）+ 三处条件拆分的 bun 分支（node 分支已存在）。另 `#fff` node 分支 `available()=false` 优雅降级 JS 搜索，无需原生编译。
- O4：opencode 服务端内嵌 Web UI 的形态（`OPENCODE_DISABLE_EMBEDDED_WEB_UI`）——能否作为 `serve`+浏览器兜底方案，与 SolidJS 渲染层方案做对比取舍？
